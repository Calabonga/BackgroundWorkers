Проведи анализ GitHub issue #$ARGUMENTS в этом репозитории и подготовь план её реализации.

## Порядок действий

1. **Получи issue.** `gh issue view $ARGUMENTS --json title,body,labels,comments,state`. Если issue уже закрыт — сообщи об этом и уточни у пользователя, нужно ли продолжать.

2. **Разберись в формулировке.** Заголовок и описание issue могут быть неточными или неполными (см. прецедент issue #187: заголовок обещал одно, а по факту требовалось другое, и у запрошенного API не было официальной поддержки). Не начинай планировать код по первому прочтению — сверь формулировку с тем, что реально возможно и что уже есть в кодовой базе.

3. **Изучи кодовую базу.** Найди существующие паттерны, интерфейсы, утилиты, которые относятся к теме issue (Explore-агенты, Grep/Glob). Проверь, есть ли применимый skill в `.claude/skills/` — если да, загрузи и следуй ему.

4. **Проверь техническую осуществимость до планирования кода**, если задача завязана на внешний API/сервис:
   - есть ли официальный документированный API для нужного действия;
   - если нет — есть ли надёжные (протестированные, с открытым кодом) сторонние клиенты;
   - если и их нет — какой ценой обошёлся бы реверс-инжиниринг (риски: ToS, secrets, общий ресурс с UI провайдера — см. `.claude/skills/feed-provider-integration/SKILL.md` как образец такого анализа для похожих интеграций).
   - Используй `gh api "search/repositories?q=..."` для поиска существующих реализаций, если `WebSearch`/`WebFetch` недоступны в среде.

5. **Не делай предположений молча.** Если возможны несколько трактовок задачи, есть архитектурные развилки, или обнаружен блокер (нет API, есть риск для аккаунта/данных пользователя, конфликт с уже принятыми решениями) — задай уточняющий вопрос через AskUserQuestion, прежде чем писать план реализации. Если по итогам анализа задачу разумно не реализовывать — прямо предложи это как вариант вместе с обоснованием.

6. **Оформи результат:**
   - Если реализация целесообразна — напиши план по правилам plan-mode этого проекта (Context → предположения/находки → предлагаемый подход → файлы для изменения → верификация), следуя `.claude/CLAUDE.md` и `.claude/rules/*`.
   - Если по итогам анализа реализация нецелесообразна (нет надёжного API, неприемлемый риск и т.п.) — изложи анализ и после согласования с пользователем закрой issue (`gh issue close $ARGUMENTS --reason "not planned"`, добавь обосновывающий комментарий через `gh issue comment`, при наличии — метку `wontfix`).

Не вноси изменения в код и не закрывай issue без явного согласия пользователя на итоговый план или на закрытие.
